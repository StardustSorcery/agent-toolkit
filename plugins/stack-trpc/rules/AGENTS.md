# tRPC Architecture Guidelines

本ドキュメントは、tRPC を採用したフルスタック構成において、エンドツーエンドの型安全性、shared パッケージによる型共有境界、バックエンドの router 実装パターン、およびフロントエンド client の利用原則を定めます。

---

## 1. エンドツーエンド型安全と境界保護の原則

1. **実装コードと型の厳格な分離**:
   - フロントエンド（クライアント側）がバックエンドの実装コード（データベース接続、秘密鍵、ORM 等）を誤ってバンドルに含めないよう、**型情報のみ (`import type`)** を共有します。
2. **Shared パッケージによる型仲介**:
   - モノレポにおいては、共通パッケージ（例: `@scope/shared-types` や `@scope/api-interface`）にルーターの型定義や DTO/Schema を集約し、フロントエンドとバックエンドの双方がそこを参照する疎結合な設計を推奨します。

---

## 2. バックエンド Router 実装原則

1. **入力バリデーションの必須化**:
   - すべての query / mutation プロシージャは、Zod 等のスキーマバリデーションライブラリを用いて入力を明示的にバリデーションしなければなりません。
2. **`satisfies` パターンによるルーター実装**:
   - shared パッケージ等で定義されたルーターインターフェース・型コントラクトを満たしていることを保証するため、`satisfies` 演算子を活用して型安全性を担保します。
3. **Context の責務分離**:
   - 認証ユーザー情報、セッション、DB クライアントなどは `createContext` で注入し、プロシージャ本体が直接グローバルインスタンスに依存することを防ぎます。

---

## 3. フロントエンド Client 生成および利用原則

1. **クライアントインスタンスの単一管理**:
   - tRPC クライアントはアプリケーション単位でシングルトンとして初期化するか、React Query プロバイダー等のフレームワークコンテキストを介して提供します。
2. **型安全なクエリフックの活用**:
   - `@trpc/react-query` または類似の公式アダプタを介して型推論の恩恵を最大化し、手動の型アサーション（`as Type`）を排除します。
